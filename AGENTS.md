# Working rules

- Never read `.env`; contextual review takes explicit configuration and does not load dotenv.
- Install the repository decision/review path with `uv sync --locked --extra worker --extra backend`.
- Task 3 focused checks: `uv run --locked --extra worker --extra backend python -m pytest -q tests/test_contextual_review.py tests/test_contextual_provider.py`.
- Task 1 integration regression checks: add `tests/decision_context` to that pytest command. Its Postgres tests use a disposable local instance and skip when the required binaries are unavailable.
- Lint new review code with `uv run --locked --extra worker --extra backend ruff check ingestion/contextual_prompt.py rules_ingestion/contextual*.py tests/test_contextual_review.py tests/test_contextual_provider.py`.
- Tests must not call paid APIs or shared databases. Scripted review fixtures are contract tests, not measured LLM accuracy.
- Keep `evaluation-result/1` immutable. Confirmed submitted/processed database duplicates reject; do not call them paid without payment evidence. Review artifacts never authorize payment.
- `rules_ingestion` is a repository API, not included in the ingestion wheel. Task 3 is not wired into `alberto/` or the frontend.
- `benchmark/schemas` is the extraction schema source of truth; packaged wheels carry copies under `ingestion/schemas`. Do not edit benchmark code/references/reports, existing provider prompts, or pipeline/config settings unless the task requires it.
- For packaging-only changes, refresh the lockfile with `uv lock --offline` without upgrading dependencies.
- The canonical end-to-end backend is `python -m backend.run_revision invoice.pdf --request-key INTENT --evaluation-date YYYY-MM-DD --input-dir PDF_DIR --sources SOURCES_YAML`. It requires Supabase, builds rules with the existing AI pipeline by default, then runs persisted extraction, the v2 evaluator, and mandatory contextual review. `backend.server` uses this same path and Postgres results; no SQLite fallback. The lower-level `InvoiceDecisionEngine` API can evaluate/review already-persisted extractions separately.
- Core CLI: `python -m rules_ingestion.engine_cli evaluate --input-id UUID --interpreter deepseek --ruleset PATH --rule-source NAME=PATH --snapshots PATH --evaluation-date YYYY-MM-DD --captured-at TIMESTAMP`; repeat `--rule-source` for every original XLSX/CSV/profile/mapping input. Source lineage is caller-attested, not proof of which historical bytes generated an existing ruleset.
- Core review CLI: `python -m rules_ingestion.engine_cli review --record-id er_HASH --request-key INTENT --reviewed-at TIMESTAMP --endpoint HTTPS_URL --model MODEL` uses explicitly supplied `REVIEW_API_KEY` in the process environment. Reusing an intent cannot repeat an in-flight/unknown provider call; a new key is an explicit new attempt. `show --record-id er_HASH` verifies saved records without paid calls.
- Core persistence requires the `core_engine_records` migration, Postgres credentials and a private Supabase Storage bucket; no local fallback. Migration/backfill against shared systems needs separate approval. Snapshots remain explicitly supplied authority/coverage assertions, not inferred complete history.
- Backend configuration is explicit process environment, never dotenv: existing Supabase/ingestion credentials plus `REVIEW_ENDPOINT`, `REVIEW_MODEL`, `REVIEW_API_KEY`; default rule generation additionally requires `JEV_API_KEY` and `DEEPSEEK_API_KEY`. `--ruleset PATH --rule-source NAME=PATH` pins an existing ruleset instead of regenerating it (or `REVISION_RULESET_PATH` plus JSON `REVISION_RULE_SOURCES`). `--status-key INTENT` retrieves a durable run without local PDFs; repeating an in-flight/unknown intent never automatically reissues paid work.
- Core/backend checks: `uv run --locked --extra worker --extra backend python -m pytest -q tests/decision_context/test_backend_engine.py tests/decision_context/test_core_engine.py tests/test_core_engine_review.py`. These use disposable local Postgres and mocked Supabase Storage/provider responses.
